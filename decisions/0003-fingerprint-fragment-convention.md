# 0003: Fragments of generated keys are the key fingerprint

- Status: accepted
- Date: 2026-11-05
- Driving work: the first release of the did:peer numalgo 4 driver.
- Affects: this repo's `src/inputDocument.ts` (`addVerificationMethod`) and
  `src/DidPeerDriver.ts`, and consumers that derive did:peer DIDs or look up
  methods by id.

## Context

A numalgo 4 input document needs a relative id for every verification method
the library generates. The fragment is part of the encoded document, so it is
part of the DID. It cannot change once a DID is issued.

The ecosystem is split. `@interop/did-method-key` and
`@interop/did-web-resolver` use the key's multibase value as the fragment.
`@interop/did-method-webvh` defaults to the last 8 characters of that value
and offers the full value only as an opt-in mode. The Python reference helper
uses indexed `#key-N` fragments.

## Decision

The fragment of a library-generated verification method is the key pair's
`fingerprint()`. For Ed25519 this is the `z6Mk...` Multikey value, and for
X25519 it is `z6LS...`. A generated method id is therefore `#z6Mk...`. A
caller may override the fragment per key with the `fragment` option.

Precondition: the suite's `fingerprint()` equals its `publicKeyMultibase`.
This holds for the Ed25519 and X25519 suites. A suite where it differs
produces ids that do not repeat the key value. That is allowed but is not the
documented shape.

This aligns did:peer with the two did-io drivers. It keeps `keyPairs` lookups
and `methodFor()` consistent across drivers.

## Rejected Alternatives

- Indexed `#key-0`, `#key-1` in insertion order, as in the Python helper.
  These are shorter. They follow a different convention from the did-io
  drivers, and the index carries no information.
- A truncated slice of the multibase value, such as the first 8 characters in
  the spec tutorial or the last 8 in did-method-webvh. This loses the
  self-describing property of the full value. The saving does not matter next
  to the length of the long form.

## Consequences

- Generated documents repeat the key value in both the method id and
  `publicKeyMultibase`, as did:key and did:web documents do.
- Long forms are longer than with truncated or indexed fragments.
- Wire artifact: a DID generated by this library encodes these fragments for
  life. A change of convention yields different DIDs for the same keys.
- The ecosystem remains split with did-method-webvh. Code that moves between
  did:peer and did:webvh cannot assume one fragment convention.
- Test vector 2 and the other published vectors use `#key-N` or truncated
  fragments. They test the codec, not the shape `generate()` produces.

## Revisit Criteria

Reopen this decision when one or more of the following holds:

1. did-method-key and did-web-resolver change their fragment convention.
2. A key suite is registered whose `fingerprint()` differs from its
   `publicKeyMultibase`, and the resulting ids cause real lookup failures.
3. A DIDComm interop partner rejects or mishandles long fragments.

If revisited, add a new convention as an explicit option. Do not change the
default for DIDs that already exist.
